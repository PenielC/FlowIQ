# FlowIQ

AI Cash Flow Intelligence Platform for African SMEs — predicting cash flow, automating financial categorisation, and improving collection of outstanding invoices through AI.

See [CLAUDE_FLOWIQ.md](CLAUDE_FLOWIQ.md) for full product, architecture, and engineering standards, and [docs/BRAND.md](docs/BRAND.md) for brand identity and colors.

## Structure

```
/src
  /FlowIQ.Api             - ASP.NET Core Web API
  /FlowIQ.Application     - Application layer (CQRS, use cases)
  /FlowIQ.Domain          - Domain entities, value objects
  /FlowIQ.Infrastructure  - EF Core, external services
  /FlowIQ.Contracts       - Shared DTOs/contracts
  /FlowIQ.Tests           - Unit & integration tests

/apps
  /web      - React web app
  /mobile   - React Native mobile app

/assets/brand  - Logo and brand identity assets
/docs          - Project documentation
```

## Backend — Running Locally

Requires the .NET 10 SDK.

```bash
dotnet restore
dotnet build
dotnet run --project src/FlowIQ.Api
```

Start the local database first — see [Local Development Environment](#local-development-environment) below.

- Swagger UI: `http://localhost:<port>/swagger` (Development only)
- Health check: `http://localhost:<port>/health`
- `appsettings.Development.json` ships with a dev-only JWT secret and a local Postgres connection string (`flowiq_dev` on `localhost:5433`, matching `docker-compose.yml`) so the API boots without extra setup. Production secrets are injected via environment variables — never commit real secrets to `appsettings.json`.

### Backend layout
- `FlowIQ.Domain` — entities, value objects, domain events (no external dependencies)
- `FlowIQ.Application` — CQRS commands/queries via [Mediator](https://github.com/martinothamar/Mediator) (source-generator based, MIT-licensed — chosen over MediatR, which requires a paid license past $5M revenue), FluentValidation pipeline behavior
- `FlowIQ.Infrastructure` — EF Core + Npgsql `ApplicationDbContext`, generic repository, unit of work, EF Core migrations (`Persistence/Migrations/`)
- `FlowIQ.Contracts` — shared DTOs (`ApiResponse<T>`, `PagedResult<T>`)
- `FlowIQ.Api` — controllers, Serilog structured logging, correlation-ID + global exception middleware, JWT bearer auth, health checks, Swagger, `Dockerfile`
- `FlowIQ.Tests` — xUnit + AwesomeAssertions (MIT-licensed FluentAssertions fork — the original went commercial at v8) + Moq

Each layer's module folders (`Authentication`, `CompaniesAndTeams`, `BankTransactions`, `AiCategorisation`, `CashFlowForecasting`, `Invoicing`, `StripeSubscriptions`, `ReportsAndAnalytics`) are scaffolded, ready for feature work — `Authentication`, `BankTransactions`, `Invoicing`, `CompaniesAndTeams`, `AiCategorisation`, `CashFlowForecasting`, and `ReportsAndAnalytics` are implemented end-to-end; `StripeSubscriptions` is still empty.

### Authentication module (implemented)

- **Application**: `RegisterCommand`, `LoginCommand`, `RefreshTokenCommand`, `GetCurrentUserQuery`, each with FluentValidation validators
- **Infrastructure**: BCrypt password hashing, JWT access tokens (HMAC-SHA256) + opaque refresh tokens, EF Core repositories
- **Api**: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`, `GET /api/auth/me` (`[Authorize]`)
- Registering creates a `Company` + `User` (role `Owner`) together — there's no separate "join a company" flow yet (that's `CompaniesAndTeams` work)
- Verified end-to-end against a real Postgres instance and through the actual web and mobile UIs (register → dashboard → logout → login → session persists across reload)

- **Api**: `POST /api/transactions`, `GET /api/transactions` (paginated), `GET /api/transactions/summary` — all `[Authorize]`, scoped to the caller's company via the `company_id` JWT claim

- **Domain**: `Invitation` (`Email`/`Role`/opaque `Token`/`InvitationStatus`, `Accept()`/`Revoke()` domain methods), `User.ChangeRole()` added to `Authentication`
- **Application**: `CreateInvitationCommand` (Owner/Admin only; rejects if the email is already registered or already has a pending invite), `AcceptInvitationCommand` (public — creates the `User`, marks the invitation accepted, auto-logs in via the same `AuthResult` shape as Register/Login), `RevokeInvitationCommand`, `UpdateTeamMemberRoleCommand`/`RemoveTeamMemberCommand` (Owner only; both block acting on yourself and demoting/removing the last remaining Owner), `GetTeamMembersQuery`/`GetPendingInvitationsQuery`

Fixed with an `ApplicationDbContext.SaveChangesAsync` override that stamps them from `IDateTimeProvider` on Added/Modified entries. This affects every entity across every module, not just this one.
- Verified end-to-end via the real UI on both web and mobile, using two real browser contexts to simulate inviter and invitee: invite → copy link → accept in a fresh unauthenticated session → new member correctly scoped to the same company with a fresh dashboard → role change and self-service guardrails (can't demote/remove yourself, can't remove the last Owner, Member/Admin-only actions correctly return 403) all confirmed against the real API.

### Cash Flow Forecasting module (implemented)
- **Application**: `GetCashFlowForecastQuery` (`HistoryDays`/`ForecastDays`, both default 30) — a deterministic trend-based projection, **not** a call to an external AI/ML service. Computes a baseline balance from all transactions before the history window, walks forward day-by-day building a running actual balance from real transactions, then projects forward using `avgDailyChange = netChangeOverHistory / HistoryDays`. No new Domain entity or migration — it's a pure query over existing `Transaction` data. `ITransactionRepository` gained `GetBalanceBeforeDateAsync`/`GetInDateRangeAsync` to support it.
- **Api**: `GET /api/forecast?historyDays=&forecastDays=` — `[Authorize]`, scoped per-company. Returns a list of `{ dateUtc, actual, forecast }` points; the last actual day carries both values so a chart's solid/dashed lines visually connect.
- Feeds the dashboard's Cash Flow Forecast chart on both web and mobile (previously mock data) with real projected numbers, plus a new dedicated `/forecasting` page on web with a 30/60/90-day range switcher and summary stat cards (current balance, projected balance, projected change). Mobile's Home screen "Forecast" stat tile now shows the real projected end-of-window balance and % change instead of the hardcoded `$58,230`/`↑18%`; AI Insights remains mock (belongs to `AiCategorisation`/insights work, not yet built).
- Verified end-to-end: unit tests cover the exact projection arithmetic and null-field correctness (history points have `forecast == null` except the connecting last-actual day; future points have `actual == null`); a real Playwright run against the live API/Postgres seeded 10 days of trending transactions and confirmed both the dashboard chart and the new Forecasting page render the correct numbers with no console errors, including switching ranges.

### AI Categorisation module (implemented)
- **Application**: `TransactionCategorySuggester` — a keyword-scoring heuristic classifier, **not** a call to an external AI/ML service (same honest-implementation approach as `CashFlowForecasting`). Each `TransactionCategory` has a set of trigger words/phrases; the description is scored against every category (case-insensitive substring match) and the highest-scoring one wins, with confidence scaled by match count and capped at 0.95. Falls back to `Other` with 0 confidence when nothing matches. `SuggestCategoryQuery` wraps it as a stateless Mediator query — no repository, no persistence.
- **Api**: `POST /api/categorisation/suggest` (`{ description }` → `{ category, confidence }`) — `[Authorize]`, not company-scoped since it's a pure function over the input text.
- Wired into the "Add Transaction" form on both web and mobile: typing a description (debounced 400ms) auto-selects the suggested category and shows a "Suggested from description" hint, but only until the user manually picks a category themselves — once touched, further typing no longer overwrites their choice. Mirrors the debounce pattern already used elsewhere, careful to only call `setState` from inside the async `.then()`/`setTimeout` callback (not synchronously in the effect body) to avoid the `react-hooks/set-state-in-effect` lint rule both platforms enforce.
- Verified end-to-end: 9 unit tests cover keyword matching per category, case-insensitivity, empty/no-match fallback, and confidence scaling with more matches. A real Playwright run against the live API/Postgres confirmed the suggestion API classifies correctly, the web and mobile "Add Transaction" forms both auto-select the right category with the hint visible, and that a manual override survives further typing on both platforms.

### Reports & Analytics module (implemented)
- **Application**: `GetReportsSummaryQuery` (`MonthsBack`, default 6, clamped 1–24) returns a monthly revenue/expense trend (reuses the existing `GetTotalsForMonthAsync` per month), an expense-only category breakdown for the trend window (groups negative-amount transactions by `TransactionCategory`, sorted descending), and an invoice status breakdown (new `IInvoiceRepository.GetStatusBreakdownAsync` — count + total amount grouped by `InvoiceStatus`). `GetTransactionsForExportQuery` reuses the existing `GetInDateRangeAsync` for CSV export, defaulting to the last 3 months when no date range is given.
- **Api**: `GET /api/reports/summary?monthsBack=` and `GET /api/reports/export/transactions?startDate=&endDate=` (streams a `text/csv` file with `Content-Disposition: attachment`) — both `[Authorize]`, per-company scoped.
- Replaces the web `/reports` placeholder: a Revenue vs Expenses bar chart, a Spending by Category breakdown with proportional bars, an Invoices by Status list, and an "Export Transactions CSV" button. **Mobile deliberately has no Reports screen** — the app's tab-based `expo-router/ui` navigation isn't set up for a 5th destination without restructuring the tab bar, and detailed reporting/CSV export is a web-appropriate workflow the way it is on most fintech products; this mirrors the same "web gets the full surface, mobile doesn't force-fit everything" call already made for `CashFlowForecasting`'s dedicated page.
- Fixed a real cross-cutting CORS gap found while wiring the CSV export: `Content-Disposition` isn't in the CORS default-exposed-headers allowlist, so the browser silently couldn't read the server-provided filename even though the download itself worked — fixed by adding `.WithExposedHeaders("Content-Disposition")` to the CORS policy in `Program.cs`. Worth remembering for any future file-download endpoint.
- Verified end-to-end: unit tests cover trend point count/ordering, `MonthsBack` clamping, category breakdown filtering/summing/sorting (expenses only, `Sales` excluded), and invoice status pass-through. A real Playwright run seeded 3 months of transactions across 4 categories plus 3 invoices in different statuses, confirmed the bar chart and both breakdown lists render the exact expected numbers, and drove a real CSV download end-to-end (correct rows, correct filename after the CORS fix).

### Stripe Subscriptions module (implemented)
- **Domain**: `Subscription` (one per company: `PlanKey`, `StripeCustomerId`, `StripeSubscriptionId`, `Status`, `CurrentPeriodEndUtc`) and `ProcessedWebhookEvent` (records a Stripe event id once handled, so retried/duplicate webhook deliveries are safely ignored — the spec's "duplicate Stripe webhook protection" and "safe retry" requirements).
- **Application**: `SubscriptionPlanCatalog` is a small fixed, hardcoded catalog (`starter` $29/mo, `growth` $79/mo) — not a database-managed product catalog, since two tiers doesn't warrant one. Each plan maps to a Stripe Price found-or-created by `lookup_key` at checkout time (`IStripeGateway`), so nothing needs pre-configuring by hand in the Stripe dashboard. `CreateCheckoutSessionCommand`/`CreateBillingPortalSessionCommand` wrap Stripe Checkout and the Billing Portal (both Stripe-hosted pages — no custom card form, no PCI scope). `ProcessStripeWebhookCommand` verifies the Stripe signature, checks the idempotency table, and updates the matching `Subscription`'s plan/status/period-end from `customer.subscription.{created,updated,deleted}` events (the subscription object itself, not `checkout.session.completed`, is the source of truth per Stripe's own recommended integration pattern). `IStripeGateway` keeps all Stripe SDK types out of Application — Infrastructure maps everything to a plain `StripeWebhookEvent` record.
- **Api**: `GET /api/subscriptions/plans`, `GET /api/subscriptions/status` (`[Authorize]`, any company member), `POST /api/subscriptions/checkout-session` / `POST /api/subscriptions/billing-portal-session` (`[Authorize(Roles="Owner")]` — billing is an Owner-only action, same convention as team role changes), `POST /api/subscriptions/webhook` (`[AllowAnonymous]`, reads the raw request body for signature verification, returns 400 on an invalid Stripe signature).
- **Real Stripe sandbox verified** (not mocked): registered a fresh account, called `checkout-session` and `billing-portal-session` against the live Stripe test API and got back real URLs; a Playwright run clicked "Subscribe to Starter" on the web `/subscriptions` page and followed the actual redirect to `checkout.stripe.com`, confirming a genuine Stripe Checkout page rendered with the correct plan name and price. Hit one real account-specific issue along the way: this Stripe account has "Managed Payments" on by default, which requires a product tax code on every line item — fixed by explicitly opting the Checkout Session out via `ManagedPayments = new SessionManagedPaymentsOptions { Enabled = false }`.
- **Config**: `Stripe:SecretKey` / `Stripe:WebhookSecret` are read from configuration (empty in `appsettings.Development.json`, meant to be set via `dotnet user-secrets` — never committed) — `App:WebBaseUrl` builds the Checkout/portal return URLs.
- 12 unit tests cover checkout-session customer reuse, plan validation, portal-session error handling, and — most importantly — the webhook handler's idempotency (duplicate event ids are no-ops), status/plan/period-end mapping, and graceful handling of events with no matching local subscription.
- **Live webhook round-trip verified** using `stripe listen --forward-to localhost:5112/api/subscriptions/webhook` (the CLI is installed locally at `%USERPROFILE%\.local\bin\stripe.exe` — portable binary, not via Chocolatey, see the FlowIQ project memory for why) plus `stripe trigger`/`stripe events resend` (Stripe's own documented tools for testing webhooks locally, used in place of automating Stripe Checkout's deeply-nested, security-hardened card-entry iframes, which proved too brittle for reliable browser automation). Attached a real Stripe test card (`pm_card_visa`) to one of our real checkout-created customers, then triggered a real signed `customer.subscription.created` event targeting that customer and our real auto-created `starter` price — confirmed in Postgres that the matching `Subscription` row updated correctly end-to-end: `Status` → `Active`, `PlanKey` → `starter` (round-tripped through the real Price's `lookup_key`), `StripeSubscriptionId` set, `CurrentPeriodEndUtc` one month out. Separately resent the exact same event id and confirmed the idempotency guard worked live (200 response in ~8ms, no duplicate row update, no duplicate `ProcessedWebhookEvents` insert — only the existence check ran).
- Mobile's "Billing" section (under the "More" tab) mirrors the web flow but opens the Stripe-hosted checkout/portal URL in the system browser via `Linking.openURL` rather than embedding it — no dedicated Stripe UI needed on mobile.

### AI Insights module (implemented)
- **Application**: `GetAiInsightsQuery` — deterministic, rule-based insights computed from real transaction/invoice data, **not** a call to an external AI/ML service (same honest-implementation approach as `CashFlowForecasting`/`AiCategorisation`). Three independent rules, each only adding an insight when it actually applies: (1) a cash flow trend insight reusing the same balance-history math as forecasting (`GetBalanceAsync`/`GetBalanceBeforeDateAsync` over the last 30 days), positive tone if growing, warning if shrinking, omitted entirely if the change is exactly zero or the current balance is zero (no divide-by-zero); (2) an "at risk" invoices insight from a new `IInvoiceRepository.GetAtRiskSummaryAsync` (unpaid invoices overdue or due within 7 days), with correct singular/plural grammar; (3) a spending-category-spike insight comparing this month vs last month's expense totals per category, only flagging a category with both a minimum absolute spend and a ≥15% increase over a nonzero prior-month baseline (avoids noise from tiny amounts or brand-new categories with nothing to compare against).
- **Api**: `GET /api/insights` — `[Authorize]`, per-company scoped, returns a list of `{ title, description, tone }` (tone: `Positive`/`Warning`/`Caution`).
- Replaces the dashboard's `AiInsightsCard` mock data on web (the "View all" link, which pointed nowhere, was dropped along with the dead `mockData.ts` file) and the mobile Home screen's hardcoded "AI Insight" banner (now shows the highest-priority real insight, or hides the whole card when there's nothing to flag) — both platforms already had the loading-prop pattern established by other cards, wired the same way.
- Verified end-to-end: 10 unit tests cover each rule's insight-present/insight-omitted branches (balance growth/shrinkage/no-change/zero-balance, at-risk count singular vs plural, category spike detection vs below-threshold vs no prior-month baseline). A real Playwright run seeded data to trigger all three rules simultaneously (a growing balance trend, an overdue invoice, a Utilities spending spike) and confirmed the dashboard and mobile Home screen both rendered the exact real, computed insight text — not mock copy.

### Company currency setting (implemented)
- **Domain**: `Company` gained `Currency` (3-letter ISO code, defaults `"USD"`), `SetCurrency()` domain method. Every amount in the app was previously shown with a hardcoded `$` — a real mismatch for a product pitched at African SMEs.
- **Currency flows through the existing auth response**, the same way `CompanyName` already did — `AuthResult`/`CurrentUserResult`/`AuthResponse`/`UserResponse` all gained `CompanyCurrency`, threaded through the 5 handlers that build them (`RegisterCommandHandler`, `LoginCommandHandler`, `RefreshTokenCommandHandler`, `GetCurrentUserQueryHandler`, `AcceptInvitationCommandHandler`). This means `useAuth()`'s `user.companyCurrency` is available everywhere on both platforms for free, no new per-component fetch.
- **Api**: `PUT /api/companies/currency` — `[Authorize(Roles = "Owner")]` (mirrors the logo upload's Owner-only convention), validated against a curated `HashSet` of ~18 supported codes (major African currencies + USD/EUR/GBP — not the full 180+ ISO 4217 list, which would need a searchable picker for currencies this product's users will essentially never pick).
- **`formatCurrency`'s signature changed** (both platforms' `lib/categoryDisplay.ts`) from `(amount) => string` (bare number) to `(amount, currencyCode) => string` (full string *with* symbol, via `Intl.NumberFormat`) — a deliberate breaking change used as a forcing function: every one of the ~25 call sites across both apps that used to manually prepend a literal `$` was flagged by the compiler and swept in one pass, so none could be silently missed.
- **Web**: new "Currency" row in Settings' existing "Company Profile" card (a `<select>` of the curated list, Owner-only) calls a new `AuthContext.refreshUser()` (re-runs `/api/auth/me`) on save, so every already-open page reflects the new currency immediately — verified via Playwright that changing currency then navigating via a real `<Link>` click (not a page reload) shows the new currency, with zero full-page `load` events firing in between.
- **Mobile has no picker UI** (no company-profile screen exists there, same reasoning as the logo upload) but **does pick up the display change** — same `user.companyCurrency` flows through mobile's own `AuthContext`, verified by setting a non-USD currency on web then logging into the same account via the Expo web preview.
- Verified end-to-end: 2 new unit tests (`UpdateCompanyCurrencyCommandHandlerTests`). A real Playwright run confirmed the full flow on web (fresh account defaults to `$`, change to KES/NGN/ZAR propagates to Dashboard/Invoices/Reports including the two Recharts chart formatters, which are easy to miss) and on mobile (Expo web preview only — this verifies the JS formatting logic and `react-native-web` rendering path, but **not** the native Hermes engine on a real device/simulator, which wasn't available to test in this environment; worth a quick spot-check there before shipping).

```bash
docker compose up -d      # starts Postgres (5433) + Redis (6380)
dotnet ef database update --project src/FlowIQ.Infrastructure --startup-project src/FlowIQ.Api
```

`docker-compose.yml` deliberately uses non-default host ports (`5433`, `6380` instead of `5432`, `6379`) since local dev machines commonly run Postgres/Redis for other projects too — `appsettings.Development.json` already points at these. If those are *also* taken, copy `.env.example` to `.env` and override `POSTGRES_PORT`/`REDIS_PORT` (then update the connection strings in `appsettings.Development.json` to match).

Redis isn't consumed by any code yet (`Redis:ConnectionString` config key is there for when caching is actually needed) — it's standing infrastructure ahead of that work, per the spec's Performance standards.

To stop: `docker compose down` (add `-v` to also delete the data volumes).

### Building the API image

`src/FlowIQ.Api/Dockerfile` is a multi-stage build, verified to build and run successfully (build from the repo root so it can see the `.slnx` and every project):

```bash
docker build -f src/FlowIQ.Api/Dockerfile -t flowiq-api .
docker run --network flowiq_default -p 8080:8080 \
  -e ConnectionStrings__DefaultConnection="Host=flowiq-postgres;Port=5432;Database=flowiq_dev;Username=postgres;Password=postgres" \
  -e Jwt__Secret="<32+ char secret>" \
  flowiq-api
```
(`--network flowiq_default` puts it on the same Docker network as the Compose Postgres container, so it can reach it by container name rather than `localhost`.)

## Deployment (Render + Neon)

`render.yaml` at the repo root is a [Render Blueprint](https://render.com/docs/blueprint-spec) defining two services: `flowiq-api` (the Dockerfile above, deployed as a Render Web Service) and `flowiq-web` (a Render Static Site built from `apps/web`). Connect the Blueprint to the GitHub repo in the Render dashboard and it provisions both.

Two real fixes were needed beyond just "have a Dockerfile" for this to actually work behind Render's reverse proxy:
- **`app.UseForwardedHeaders(...)`** in `Program.cs`, before `UseHttpsRedirection()` — without it, the container (which receives plain HTTP from Render's TLS-terminating edge) thinks every request is HTTP and redirects to HTTPS forever, since it never sees `X-Forwarded-Proto`.
- **A SPA rewrite rule** (`/* → /index.html`) on the static site — otherwise a browser refresh on any deep React Router route (e.g. `/dashboard`) 404s, since the static host has no idea `/dashboard` isn't a real file.

### One-time setup
1. **Neon**: create (or confirm) a Neon project for FlowIQ, grab its pooled connection string.
2. **Apply migrations to the real database once**, from your machine, before the first deploy:
   ```bash
   $env:ConnectionStrings__DefaultConnection = "<neon-connection-string>"   # PowerShell; use export on bash
   dotnet ef database update --project src/FlowIQ.Infrastructure --startup-project src/FlowIQ.Api
   ```
3. **Connect the Blueprint** in the Render dashboard (New → Blueprint → this repo).
4. **Fill in the `sync: false` values** Render will prompt for (never committed to git):
   - `flowiq-api`: `ConnectionStrings__DefaultConnection` (the Neon string from step 1), `Redis__ConnectionString` (Upstash — copy the StackExchange.Redis-compatible connection string, e.g. `endpoint:port,password=...,ssl=True`, from the Upstash dashboard; nothing consumes this yet, it's standing infra ahead of the caching work), `Stripe__SecretKey`/`Stripe__WebhookSecret` (**use Stripe *test* keys for the first deploy** — switching to live keys is a separate, deliberate step once ready to accept real payments), `Email__ResendApiKey`/`Email__FromAddress` (Resend — powers the forgot-password flow; `onboarding@resend.dev` works as `FromAddress` without domain verification for initial testing), `Cors__AllowedOrigins__0` and `App__WebBaseUrl` (leave blank for the very first deploy — see step 5)
   - `flowiq-web`: `VITE_API_URL` (leave blank for the very first deploy too)
   - `Jwt__Secret` is auto-generated by Render (`generateValue: true`) — don't reuse the dev-only secret from `appsettings.Development.json`
5. **Two-pass URL wiring**: since each service's public URL isn't known until Render assigns it, deploy once with the three blanks above empty, note both services' actual `https://flowiq-*.onrender.com` URLs, then go back into the dashboard and set `VITE_API_URL` (on `flowiq-web`) to the API's URL and `Cors__AllowedOrigins__0`/`App__WebBaseUrl` (on `flowiq-api`) to the web URL — each with the full `https://` scheme, not just the bare hostname. Redeploy both.
6. **Admin access**: `Admin__AllowedEmails__0` is pre-set in `render.yaml` to the founder's email — add more via additional `Admin__AllowedEmails__N` env vars in the dashboard if needed.

### Verifying a deploy
- `GET https://<flowiq-api-url>/health` → `200`
- Register or log in against the deployed web app — confirms CORS + JWT + the Neon round-trip all work for real
- Refresh the browser on a deep route (e.g. `/dashboard`) on the deployed site — confirms the SPA rewrite rule
- Log in as an allowlisted admin, load `/admin` — confirms the production `Admin:AllowedEmails` env var took effect
- Click "Start Free Trial" on `/subscriptions` — confirms Stripe test-mode checkout is reachable end-to-end, without spending real money

### Explicitly not covered by this Blueprint
GitHub Actions CI (Render auto-deploys on push without it), production error tracking/log aggregation (Sentry etc.), real email delivery for team invites, and mobile app publishing (a separate EAS Build / App Store / Play Store process) — all real gaps, just not part of getting the web+API live.

## Mobile — Running Locally

Requires Node.js. Uses [Expo](https://expo.dev) + TypeScript + Expo Router.

```bash
cd apps/mobile
npm install
npx expo start        # then press i / a / w, or scan the QR code with Expo Go
```

Point it at a running API with `EXPO_PUBLIC_API_URL` in `apps/mobile/.env` (copy from `.env.example`, defaults to `http://localhost:5112`). `localhost` only reaches the dev machine from the **web preview** (`w`) and the **iOS simulator** (it shares the Mac's network) — it does *not* work from an Android emulator or a physical device, since `localhost` there means the device itself:
  - **Android emulator**: `http://10.0.2.2:5112` (Android's special alias for the host machine).
  - **Physical device via Expo Go**: your computer's LAN IP (e.g. `http://192.168.1.xxx:5112`, find it with `ipconfig`/`ifconfig`) — the phone and dev machine must be on the same WiFi network.
  - Either way, the API itself must also be listening on all interfaces, not just `localhost` — `src/FlowIQ.Api/Properties/launchSettings.json`'s `http` profile uses `applicationUrl: "http://0.0.0.0:5112"` for exactly this reason. If a physical device still can't connect after setting the right IP, check the Windows Firewall isn't blocking inbound connections to port 5112 on the network your PC is connected to (this wasn't verified as part of this fix — a local firewall rule may still be needed).
  - **`EXPO_PUBLIC_*` env vars are inlined at Metro bundle time** — changing `.env` requires restarting `npx expo start`, not just reloading the app.
